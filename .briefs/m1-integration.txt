## 1. Define the canonical domain types (new — `src/domain/`)

**This is the most important part of this brief.** Neither track defined `Ingredient`, and
every downstream track (seed data, matching, recipes, grocery) needs it. Extract the shapes
from `SPEC.md` — do not invent them:

```ts
Ingredient      { id, name, category, allergens[], isStaple, defaultFormId }
IngredientForm  { id, ingredientId, form, dim, densityGPerMl?, gramsPerCount?, uncertaintyPct }
ConversionEdge  { fromFormId, toFormId, factor, uncertaintyPct, source, oneWay? }
PackageSpec     { formId, label, netG, drainedG? }
Location        { id, householdId, name, icon, tint, parentId?, sortOrder }
```

Plus a canonical **allergen** enum. Per SPEC, allergens are a **safety system, not a
preference**: include at minimum the major declarable allergens (milk, egg, fish, shellfish,
tree nut, peanut, wheat, soy, sesame) and a way to represent `unknownAllergens: true` for
unmatched free text. Downstream matching must be able to refuse an auto-merge when allergen
tags disagree — make that representable here.

Track A currently owns `IngredientForm` / `ConversionEdge` / `PackageSpec` locally. Move them
to `src/domain/` and have `src/units/` import them, so the domain vocabulary has one home.
Keep `src/units/` owning the *math*; `src/domain/` owns the *shapes*.

## 4. Apply the four change requests

All four are ruled on in `.briefs/m1-integration-decisions.md`. Read it for the reasoning;
summarized here:

**(a) Bidirectional conversion edges.** Add `oneWay?: boolean` (default false). `convert()`
walks declared edges *plus* the inverse (`1/factor`) of every edge not marked `oneWay`.
Inverted edges carry the same `uncertaintyPct` and a path key that makes the inversion visible
(e.g. `b->a~inv`). Rationale: most culinary conversions are symmetric; forcing seed data to
emit both directions doubles it and lets the directions drift apart. But some are physically
lossy (whole chicken → boneless yield) and must stay one-way.
**Tie-breaking must remain deterministic with inverse edges in play** — re-verify the existing
graph tie-break tests still hold and add coverage for inverse-edge ties.

**(b) Ranges expose low/high.** `parseQuantity("2-3 cloves")` currently collapses to a
midpoint. Return `{ kind: 'quantity', qty: midpoint, low, high, isRange: true }` instead.
Grocery/shortfall will want `high` (under-buying means a second trip); pantry deduction wants
`midpoint` (deducting high drifts inventory low). Do not decide for the caller at parse time.

**(c) `ambiguousLocale` flag.** Units whose US and Imperial definitions differ — `pint`,
`quart`, `gallon`, `fl oz`, `cup` — get `ambiguousLocale: true` in their definition, surfaced
through `parseQuantity`. We stay US-only, but a UK recipe's "1 pint" is 568 ml vs our 473 ml —
a **20% silent inventory corruption**, reachable via M3 URL import. Flag it so the import path
can ask. Do not reject, do not silently assume.

**(d) Terminology fix.** Track A's code/report call `236.5882365 ml` the "US **legal** cup."
It is the US **customary** cup (1/16 gallon). The legal cup is exactly 240 ml (FDA, nutrition
labeling). **The value is correct — change only the comment.** Add a note that if nutrition
panels are ever parsed, they need a separate unit id, not a redefinition of `cup`.

## 5. Document a known limitation (do not necessarily fix)

`detectAbsoluteConflicts` in `src/pantry/fold.ts` compares each prior absolute only against the
**winner** (last in total order). With three absolutes A1, A2, A3 where A3 observed A2 but A2
never observed A1, the genuine A1/A2 conflict is not reported. Quantity remains correct; only
conflict *reporting* is incomplete.

Add a clear comment documenting this. If a fix is cheap and does not complicate the common
path, implement it and say so; if not, leave it documented and note it in your report. **Do
not silently change fold semantics to chase it** — the quantity behavior is verified and must
not regress.
