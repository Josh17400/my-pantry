## Fault 1 — the Add quantity wheel seeds at zero, so "Add to pantry" refuses

`apps/web/src/features/pantry/lib/picker-wheels.ts`, `seedPickerSelection()` returns
`{ qty: 0, ... }` for `mode: 'add'`. `AddItemSheet.submit()` then fails the
`qtyOutcome.qtyBase <= 0` guard and renders *"Quantity must be greater than zero"* in a
small `role="alert"` under the fold.

Confirmed output from the repro:

```
!! submit error: ["Quantity must be greater than zero"]
matching stored rows: []
```

So the default state of the Add sheet is one that cannot be submitted. That is the bug: a
first-time user taps Add to pantry, nothing visibly happens, and no item is created.

**Fix:** `mode: 'add'` must seed to a sensible non-zero quantity — the first non-zero step of
the seeded unit (`quantityStepsForUnit`), so `each → 1`, and mass/volume land on their first
real step rather than 0. Leave `adjust` and `waste` seeding at 0 (a signed delta defaulting to
"no change" is correct); `recount` already seeds from current stock.

If a zero quantity remains reachable, the submit error must be visible where the user is
looking — but the primary fix is that the default is valid.

## Fault 2 — the count dimension defaults to "dozen", so one cucumber becomes twelve

This one silently corrupts inventory and is the more serious of the two.

```
formatQuantity(0, 'count', { locale: 'us', uncertaintyPct: 0 })  ===  "0 dozen"
pickDefaultUnit(0, 'count')                                       ===  "dozen"
seedPickerSelection('add', 'count', 0)  === { qty: 0, unit: "dozen", direction: "add" }
```

Repro, end to end: pick Cucumber → dial the quantity wheel to **1** → the preview reads
**"Adding 1 dozen of Cucumber"** → the stored row is `qtyBase: 12`.

Two layers, and **both** are wrong:

1. `formatQuantity(0, 'count')` in `packages/core` returning `"0 dozen"`. Zero of a countable
   thing is "0 each". Nothing is ever naturally expressed as "0 dozen". Find why the formatter
   selects the larger unit at zero and fix it there. Check the same class of error at zero for
   mass and volume while you are in it — and note that `pickDefaultUnit(0, 'mass') === 'lb'`
   and `pickDefaultUnit(0, 'volume') === 'cup'`, which are defensible for a US locale but
   should be a deliberate choice, not an accident of the same code path.
2. `pickDefaultUnit` in `picker-wheels.ts` inheriting it. Its fallback scoring loop gives
   `readabilityScore(0) === 1000` for every unit, so the tie is decided by whatever
   `formatQuantity` said. Make the zero case explicit rather than emergent: for `count`,
   default to `each`, always.

`each` must be the count default in the picker regardless of what the formatter returns. Fix
the formatter *and* make the picker not depend on it.

## Fault 3 — a pantry row that renders with no name ("one each", no title)

**I could not reproduce this on a fresh catalogue** — on seed `1.1.0` the cucumber row renders
correctly as "Cucumber". Reported honestly so you do not waste time assuming it is proven:

```
catalogue: 374 ingredients, seed_version=1.1.0
  cucumber row: {"id":"cucumber","name":"Cucumber",...,"defaultFormId":"cucumber-each"}
```

The display path is `resolvePantryItemDisplayName()` in
`apps/web/src/features/pantry/components/PantryItemRow.tsx`. It deliberately returns the
string **`"Unknown item"`** when the catalogue join misses (name absent, name equal to the
ingredient id, name equal to the location name, or a raw slug/uuid). The owner describing a row
that "doesn't say what it is" is consistent with `"Unknown item"` being rendered.

The join happens in two places and both fall back to the raw id:
- `apps/web/src/db/drivers/dev.ts:305` — `ingredientName: ing?.name ?? item.ingredientId`
- `apps/web/src/db/domain-repository.ts:258,301,336` — `r.ingredientName ?? r.item.ingredientId`

**Your job:** reproduce it against *legacy device state*, not a fresh seed. The owner's install
predates `SEED_VERSION 1.1.0`. Construct a snapshot the way a real upgrading device would look
— pantry rows referencing ingredient ids that are absent from, or stale in, the local
`ingredients` table — and find the path where a freshly added item lands with an unresolvable
name. Then fix the cause.

Specifically worth checking:
- does the manual-add path write the `ingredients` catalogue row it depends on, or does it
  assume seeding already did?
- `AddItemSheet` passes `ingredientName: picked.name` to `onConfirm` — **is that name actually
  persisted anywhere**, or is it dropped, leaving display wholly dependent on the join? The
  IndexedDB records carry no `ingredientName` field at all. If the name is dropped, persisting
  it on the pantry row is the robust fix: the row then renders correctly even when the
  catalogue is stale.
- does a `SEED_VERSION` bump re-upsert the catalogue on an existing install, and does that path
  actually run on device?

Also related, same report: the owner said the row read **"French"**. The only "French" in the
entire codebase is the alias `FRENCH FRIES` / name `"Frozen french fries"` on `frozen-fries`
(`packages/core/src/seed/categories/frozen.ts:59`). Work out how a cucumber add could surface
that string — or establish that it cannot, and say so plainly in the report. A confident
"cannot happen, here is why" is a fine answer; a guess is not.
