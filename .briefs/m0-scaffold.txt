## Deliverables

### 1. Monorepo skeleton (npm workspaces)

```
Larder/
  package.json            workspaces: ["packages/*", "apps/*"]
  tsconfig.base.json      strict: true, no implicit any
  .gitignore              node_modules, .expo, dist, *.local, .env*
  packages/core/          pure TypeScript. ZERO React, ZERO react-native, ZERO platform APIs.
    src/index.ts
    package.json          vitest configured
    vitest.config.ts
    test/smoke.test.ts
  apps/mobile/            the Expo app
    app/                  expo-router routes
    src/db/               Drizzle schema + repository interface + drivers
```

`packages/core` must be importable by `apps/mobile` through the workspace. Metro needs
explicit monorepo config to resolve workspace packages — get this working, it is a known
friction point and is exactly the kind of thing M0 exists to shake out.

### 2. Expo app that boots on all three targets

- expo-router with a minimal tab layout: `Home` and `DB Health`.
- NativeWind v4 wired up (verify current compatibility with the SDK you pin — if it is
  broken against the current SDK, DO NOT fight it: report that and use plain StyleSheet for
  M0, and say so clearly in your report. Do not silently substitute something else.)
- TypeScript strict, no errors.

### 3. THE CRITICAL DELIVERABLE — the DB Health screen

This is the go/no-go gate for the entire platform choice. Build a screen that, on demand,
runs a self-test against the real local database and renders a visible PASS/FAIL per step:

1. open/create the database
2. run a Drizzle migration that creates a table
3. insert 1,000 rows in a transaction (proves batching + transactions work)
4. read them back and verify the count and checksum
5. run an indexed aggregate query and report elapsed milliseconds
6. close and reopen the DB, verify the data **persisted across reload** (this is the step
   that most often fails on web — a DB that lives only in memory passes steps 1-5 and is
   still worthless to us)
7. delete the test table, leaving no residue

Display each step's result and timing on screen. It must run identically on native and web.

### 4. The repository interface — the whole point of this structure

Define `PantryRepository` (or similarly named) in `apps/mobile/src/db/` as a
platform-agnostic interface, with the concrete driver selected per platform. For M0 the
interface only needs whatever the health check exercises — do not model the real domain yet.

**This exists so that if SQLite-on-web fails, we swap ONE file instead of rewriting the app.**
If `expo-sqlite` web support is broken, unstable, or requires server headers we cannot set on
static hosting, then implement the web driver over a different backing store (IndexedDB via
Dexie, wa-sqlite directly, OPFS, whatever actually works) behind the same interface — and
say plainly in your report what you had to do and what it costs us.

## Constraints / known traps

- **Windows paths.** Metro and monorepo symlink resolution have Windows-specific failure
  modes. If you hit one, fix it properly in config; do not work around it by flattening the
  monorepo.
- Check `npm config get os` — if it returns `linux` on this Windows machine, that is a known
  local misconfiguration in `~/.npmrc` that breaks native npm packages. Report it if seen.
- **Do NOT create a Supabase project or add Supabase credentials.** That requires the owner's
  account. Add the client dependency and a config module that reads from env, leave the env
  values empty, and note it as a handoff item.
- Do not add analytics, crash reporting, ads, or IAP. Not this milestone.
- No secrets in the repo. `.env*` is gitignored.
